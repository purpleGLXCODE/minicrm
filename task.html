Мини-CRM для заявок агентства

Рабочий MVP: Telegram → API → PostgreSQL → Web CRM

1. Набросок продукта

Задача — собрать простую CRM, в которую попадают заявки из разных источников и с которыми менеджер может работать из одного интерфейса.

Основной сценарий MVP:

Telegram → заявка → API → PostgreSQL → CRM

Telegram-бот получает текст обращения. Имя и Telegram ID берутся автоматически из Telegram, username используется как контакт. Пользователю не задаются лишние вопросы — запрашивается только сам запрос.

Что входит в MVP
  • Telegram-бот для приёма заявок;
  • автоматическое создание лида в PostgreSQL;
  • имя, username и Telegram ID из Telegram;
  • ручное добавление лида;
  • редактирование и удаление;
  • теги;
  • фильтрация по тегам;
  • отображение источника лида;
  • рабочий Web-интерфейс CRM.

Архитектура

Telegram Bot ─────┐
                  │
Manual CRM ───────┼──→ FastAPI → PostgreSQL → Web CRM
                  │
Telegram account ─┘
     (следующий этап)

Web CRM является основным продуктом, Telegram — каналом поступления данных.

Подключение обычного Telegram

Этот пункт не включён в текущий MVP. Для него предусмотрен отдельный интеграционный слой на базе MTProto/Pyrogram: входящие сообщения подключённого Telegram-аккаунта нормализуются в ту же сущность Lead и передаются через существующий API.

Что сознательно оставлено за рамками MVP

Авторизация и роли пользователей, воронка продаж, задачи, история изменений, сложная аналитика и другие Enterprise-функции.

Главная цель — сначала проверить основной рабочий контур: получение лида → сохранение → тег → работа с лидом в CRM.

2. Как делал

Сначала определил минимальный продуктовый контур и структуру данных, затем собрал backend API и PostgreSQL, после этого подключил Telegram-бота и Web CRM. В конце связал всё в единый сценарий и проверил работу через живой сервер.

Стек
  • Python 3.12
  • FastAPI
  • PostgreSQL
  • psycopg
  • aiogram
  • HTML / CSS / JavaScript
  • Nginx
  • systemd
Архитектурное решение

Для MVP сознательно не использовал ORM и frontend-фреймворк: прямой SQL и обычный JavaScript позволили быстрее собрать прозрачный рабочий контур без лишних слоёв.

AI-инструменты

ИИ использовался как инструмент разработки: для генерации и доработки отдельных частей кода, поиска ошибок, проверки архитектурных решений и ускорения итераций. Финальные решения по структуре MVP, API, модели данных и пользовательскому сценарию принимались в процессе самостоятельной разработки и проверки работающего проекта.

Что сделал бы дальше

  1. подключил бы обычные Telegram-аккаунты через MTProto;
  2. связал бы повторные сообщения пользователя с существующим лидом по telegram_id;
  3. добавил бы статусы лида и простую воронку;
  4. добавил бы историю коммуникации;
  5. добавил бы уведомления менеджеру о новых лидах.
