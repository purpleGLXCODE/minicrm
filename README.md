# MiniCRM — MVP для заявок агентства Jump Ads

Мини-CRM для обработки входящих заявок агентства.

Проект сделан как тестовый MVP для вакансии **Вайбкодер / Jump Ads**.

Главная задача MVP — показать полный рабочий контур:

**Telegram → заявка → БД → CRM → тег → фильтрация**

---

## 1. Цель MVP

Это не полноценная CRM уровня Bitrix24.

Минимальный внутренний инструмент для менеджера агентства:

- получать заявки из Telegram-бота;
- видеть их в CRM;
- добавлять лидов вручную;
- назначать теги;
- фильтровать лидов по тегам.

Обязательный пользовательский сценарий:

```
Пользователь
    ↓
Telegram-бот
    ↓
Имя
    ↓
Контакт
    ↓
Запрос
    ↓
Создание лида
    ↓
PostgreSQL
    ↓
CRM
    ↓
Тег
    ↓
Фильтр
```

---

## 2. MVP-функции

### Telegram

Бот последовательно собирает:

1. имя;
2. контакт;
3. запрос.

После третьего ответа создаётся лид в БД.

Пример:

```
Имя: Иван
Контакт: @ivan
Запрос: Нужен AI-бот для бизнеса
Источник: telegram
```

Для лидов из Telegram автоматически добавляется тег `telegram`.

---

### CRM

Основной список лидов:

| Поле | Назначение |
|---|---|
| ID | Идентификатор лида |
| Имя | Имя клиента |
| Контакт | Telegram / телефон / email |
| Запрос | Что требуется клиенту |
| Источник | Telegram / Manual |
| Дата | Время создания |
| Теги | Классификация лида |

В CRM доступны:

- список лидов;
- просмотр лида;
- ручное добавление;
- добавление тегов;
- удаление тегов;
- фильтрация по тегу.

## 4. Стек

- Python 3.12+

- Pydantic

- aiogram 3

Для MVP используется обычный HTML/CSS/JavaScript без тяжёлого frontend-фреймворка.

Цель — максимально быстро получить рабочий продукт и не тратить время на инфраструктуру, которая не нужна для поставленной задачи.

### Deployment

- Ubuntu
- Nginx

## 5. База данных

### leads

```sql
id
name
contact
request
source
created_at
```

`created_at` хранится как Unix timestamp.

### tags

```sql
id
name
```

### lead_tags

Связь many-to-many:

```sql
lead_id
tag_id
```

Такой вариант позволяет одному лиду иметь несколько тегов:

```
[telegram] [hot] [ai]
```

Источник и тег разделены намеренно:

- **source** отвечает на вопрос «откуда пришёл лид»;
- **tags** отвечают на вопрос «как классифицировать лид».

---

## 6. API

Минимальный REST API:

```
GET    /api/leads
GET    /api/leads/{id}

POST   /api/leads

POST   /api/leads/{id}/tags
DELETE /api/leads/{id}/tags/{tag}

GET    /api/tags
```

Фильтрация:

```
GET /api/leads?tag=hot
```

Пример ручного создания:

```json
{
  "name": "Иван Сидоров",
  "contact": "+79991234567",
  "request": "Хотим автоматизировать продажи"
}
```

Источник для такого лида автоматически устанавливается как `manual`.

## 8. Демонстрационный сценарий

Рабочая демонстрация должна проходить без ручного переноса данных:

### Шаг 1

Пользователь открывает Telegram-бота.

### Шаг 2

Бот спрашивает имя.

### Шаг 3

Бот спрашивает контакт.

### Шаг 4

Бот спрашивает запрос.

### Шаг 5

После последнего ответа автоматически создаётся лид.

### Шаг 6

Менеджер открывает CRM и видит новый лид.

### Шаг 7

Менеджер назначает тег:

```
hot
```

### Шаг 8

Менеджер выбирает фильтр:

```
hot
```

CRM показывает соответствующие лиды.

Это основной Definition of Done MVP.

---

## 9. Что сознательно не входит в первый MVP

Не перегружаем тестовое:

- полноценные роли и ACL;
- сложная авторизация;
- воронка продаж;
- задачи менеджеров;
- сделки;
- счета;
- аналитика;
- email;
- WhatsApp;
- интеграции с десятками сервисов;
- полноценное подключение обычного Telegram-аккаунта.

### Обычный Telegram

Получение входящих сообщений из подключённого обычного Telegram-аккаунта указано в задании как дополнительная функция.

Она может быть добавлена после выполнения обязательного сценария.

## 11. Definition of Done

MVP считается готовым, когда работает следующий путь:

```
Telegram user
      ↓
Telegram Bot
      ↓
name
      ↓
contact
      ↓
request
      ↓
lead created
      ↓
PostgreSQL
      ↓
lead visible in CRM
      ↓
manager adds tag
      ↓
manager filters by tag
```

Все этапы должны работать на живом deployment.

---

## 12. Принцип разработки

Главный принцип проекта:

> Сначала рабочий контур, затем расширение.

AI используется как инструмент ускорения разработки, но архитектура, модель данных, API и интеграционные решения контролируются разработчиком.

Для тестового задания приоритет:

1. работающий сценарий;
2. понятная архитектура;
3. простая поддерживаемая кодовая база;
4. живой deployment;
5. только после этого — дополнительные функции и визуальный polish.
